# FileAtlas canvas workspace plugin

## Ownership and source reuse

The Cordis product plugin remains `fileatlas.whiteboard` / `fileatlas/whiteboard`
for compatibility with the just-added settings, MCP names and user data. Its visible
product name is **画布**. It owns the unique canvas panel, four rail-triggered
collapsible drawers, bottom-center drawing toolbar, board switcher, resource list,
layer list, import/export and host callbacks. Board create/rename/import/export,
remove and image-cache refresh live inside the Board drawer. Style controls sit at the canvas upper-right;
undo/redo share the bottom toolbar row at its far left. Cordis owns
startup and cleanup; UI Bridge owns the rail/panel/view registrations.

The engine is the local `fileatlas-canvas-engine` workspace crate. It contains a
source copy from the registry package `gpui-whiteboard 0.5.1`, upstream commit
`d94ade3eb162c041b71994681356fcbcb4dcfd8e` (MIT). `Cargo.lock` now has no
`gpui-whiteboard` package dependency; the product links only to the FileAtlas
workspace crate. The upstream crate boundary was confirmed from its published
manifest and package source. No Zorite application crate, note store or GPL
application code was copied. Preserve `LICENSE`, bundled JetBrains Mono OFL terms,
and `assets/icons/LICENSE` (Lucide/ISC). The engine PORTS records the local
adaptations and licenses.

The engine owns Scene JSON, camera mapping, GPUI input, hit testing, selection,
transforms, drawing, edit transactions and one undo/redo history. FileAtlas-added
entry points only expose embedded mode, current elements/selection, layer selection,
paint-order movement, and existing tool-group/color/font/template UI. Layer reorder
is an engine scene edit and runs its same history, `on_change` and save path.

## Public integrations and lifecycle

- Fixed canvas chrome uses the existing `fileatlas-ui-bridge::i18n::tr` boundary.
  The host installs that translator in `fileatlas-canvas-engine`; engine tooltips,
  tool groups, formatting/font/context menus and page/image badges resolve Fluent
  messages at render time. Scene text, board names, resource titles and user data
  stay untranslated. Catalog entries live in `fileatlas-plugin-i18n/locales`.

- `WhiteboardService` is `fileatlas/whiteboard`; its versioned JSON is a modest
  whole-document library. No new database or plugin manager is introduced.
- Existing `MediaResourceService` / `ResourceProvider` is the stable resource
  contract. Provider registration returns a drop token and removes the provider at
  plugin stop. Local image/video/audio/file links share a URI and provider open path.
- `CanvasToolContribution` is the only new toolbar extension. It carries command ID,
  icon catalog key, group/order and optional shortcut; `register_tool_for_plugin`
  binds its registration token to the contributing Cordis plugin's stop lifecycle.
  The command itself still uses the owner's normal UI Bridge command registration,
  permissions and `UiCommandInvoked` observer. Built-in drawing tools remain one
  engine-owned tool set rather than per-shape plugins.
- The host's file-card action resolves the same ResourceLink then asks the provider
  to open/play; if unsupported it hands the resolved file to QuickLook. A video
  inserted as a card carries a visible `视频 ·` title prefix, remains a normal
  selectable scene element, and appears in the resources list. There is no embedded
  video playback, duration/timeline annotation, or arbitrary external card renderer.
- Image insertion, clipboard paste, drops, templates, font selection, color editing,
  import/export and scene persistence call the copied engine's existing semantics.
  No parallel canvas scene or undo stack is created.
- Native image drops from Eagle's `.info` item folder are matched through the
  optional `fileatlas/eagle-links` service. Selected image properties retain the
  Eagle item name/ID, assigned folders, original filesystem path and FileAtlas
  `file://` URI, thumbnail path, and Eagle Web API item URL. Metadata is additive
  on each board JSON record and defaults empty for existing libraries. Ordinary
  file drops remain normal local resource links.

## Storage, compatibility and recovery

Normal path: `%LOCALAPPDATA%/FileAtlas/whiteboards/library.json`.
Isolated profile: `<FILEATLAS_DEV_TEST_DIR>/whiteboards/library.json`.
Library format remains version 2; it stores board titles/IDs, opaque Scene JSON,
font links, templates, user document colors, ResourceLink URIs and active board.
Large pasted images remain separate PNGs in `whiteboards/pasted-images/`. Source
media remains external.

Image scenes keep linking the original `ResourceLink` URI. In addition, each
board's additive `image_previews` JSON field points to a board-owned JPEG under
`whiteboards/previews/<board-id>/`; insertion copies the shared thumbnail cache
asset there so later eviction of FileAtlas's shared cache cannot remove a board
preview. These assets are generated by the existing ThumbnailService (maximum
dimension 300 px); library version 2 and existing Scene JSON are unchanged.
Missing/corrupt preview assets are regenerated from the linked source on demand.
At render time the canvas starts with the thumbnail. Quality selection uses the
full transformed image rectangle in physical screen pixels, converted using the
monitor scale factor. Viewport clipping only controls painting, so panning an
image partly or fully out of view does not trigger a quality downgrade. At
500,000 pixels it requests the original; at 350,000 pixels or fewer it returns
to the thumbnail after the image remains below that threshold for 350 ms. Both
sources crossfade with 180 ms smoothstep opacity. Original decodes stay in a
memory-only cache for up to 30 seconds after last use, with a 128 MiB budget for
idle originals; least-recently-used idle entries are released first. Currently
visible originals remain usable, while expired or evicted entries decode again
on demand. Only thumbnail assets persist on disk.
The board file stores metadata, while preview JPEGs remain separate binary files.

Version 1 `path` values migrate losslessly to version 2 `uri`; old absolute image
paths still resolve. Zorite Scene JSON import/export remains compatible and leaves
image paths unchanged. Writes use a sibling temporary file and backup; a valid
`.bak` is restored on primary corruption while retaining `.corrupt`. Unsupported
future versions stop startup without overwriting source data. Import validates the
Scene before changing the library. No SQLite schema or existing FileAtlas media rows
are changed.

## MCP and debugging

Registered tools include `whiteboard.state`, `whiteboard.cache_stats`,
`whiteboard.panel`, `whiteboard.tool_group`, `whiteboard.toolbar_menu`, `.create`,
`.open`, `.scroll`, `.rename`, `.import`, `.add_images`, `.flush`, and `.export`.
`whiteboard.cache_stats` is read-only and reports current-board thumbnail/original
model entries, decoded image counts and RGBA byte estimates, source-quality state
counts, visible image count, idle original bytes, active transitions, pending
downgrades, original request/memory-hit/decode-request totals, and TTL/budget
eviction counters. The response includes the active thresholds and retention
policy. RGBA byte estimates exclude GPUI/GPU and allocator overhead. Counters
reset when the active board changes. `whiteboard.scroll`
accepts `{id, delta_x, delta_y, control, at:[x,y]}` where `at` is canvas-local
logical pixels. It queues the same `WhiteboardView::scroll_canvas` handler used
by wheel input: `control:false` zooms about the pointer; `control:true` pans.
`whiteboard.state` returns the resulting `scene.camera` for readback. Requests
are bounded to 4096 logical pixels and the queue holds at most 64 pending
gestures. This public tool requires Standard MCP access. Read state includes
board scenes and resource links. High-impact export retains Full access plus
per-call confirmation.
Canvas pointer interactions use the FileAtlas MCP `control_ui` event path against the
same GPUI child; no alternate drawing endpoint exists. Errors are visible in the
panel or save status. Inspect `.local/validation/profiles/<run>/whiteboards`,
primary/backup/corrupt files, the same-process MCP log and plugin startup diagnostics.

`whiteboard.panel {side,panel}` is a Standard-gated live UI action for the four
drawers: left accepts `boards`, `resources` or `close`; right accepts `layers`,
`object` or `close`. It queues the same Host panel state used by the drawer buttons,
opens the canvas surface, and returns when queued; use `screenshot_window` to verify
the rendered result. The queue is bounded to 16 requests and is memory-only.
`whiteboard.tool_group {group}` is a Standard-gated live canvas action for
`shapes`, `lines` or `pages_images`. The queue is bounded to 16 actions. Embedded
canvas flyouts use one fixed panel above the bottom toolbar; placement is shared
across groups and independent of button coordinates.
`whiteboard.toolbar_menu {menu}` accepts `color`, `font`, or `templates` and
opens the existing engine control through the live Host queue. Embedded color and
font panels share the fixed anchor above the bottom toolbar; templates retain the
engine's centered gallery. Both action queues are bounded to 16 requests.

## Current feature limits

Implemented in the FileAtlas shell: unique drawing toolbar, select/pan/text and tool
families for shapes, pen/connectors and resources; color/font/template access; one
undo/redo pair; image/file insertion; image/video resource listing; board list; layer
selection and up/down reorder through engine history/save; existing save/restore and
Scene import/export.

Still open: command-backed toolbar extensions cannot define new Scene element
semantics, and there is no arbitrary card renderer API; properties inspector is
read-only beyond selecting/reordering layers; layer grouping, hide/lock; resource
search/filter and video playback; nested layer UI; shortcut dispatch for the
optional toolbar shortcut metadata; full light/dark, changed-accent and narrow-window
visual coverage. The concept marks these states as future work, not shipped behavior.

Validation evidence: `docs/validation-ui/2026-10-26-fileatlas-canvas/README.md`.

Localization verification: docs/validation-ui/2026-10-26-canvas-i18n.md.

## Side-panel information layout — 2026-10-26

The left board/resource panel uses type icons, decoded/truncated names and a
compact kind/extension subtitle. The right panel renders each layer as one row
with a kind icon and icon-only up/down actions; selected-object properties use
semantic icon/value rows, short path tails, and copy buttons whose tooltips retain
the full value. Both side panels scroll vertically and keep canvas scene semantics
in the existing engine/service. Visual/runtime evidence and uncovered states are
listed in `docs/validation-ui/2026-10-26-canvas-sidepanels.md`.

Windows Explorer copy behavior: the `本地文件路径` property copies a filesystem
path with `\\?\UNC\` / `\\?\` Windows extended-path prefixes removed. The separate
`画布资源 URI` property copies the percent-encoded `file://` resource identifier
used by FileAtlas; do not paste that URI where Explorer expects a filesystem path.

For a selected image with persisted Eagle source metadata, the inspector adds an
icon button that calls the optional `EagleLinkService::open_item` operation. It
dispatches Eagle's `eagle://item/{id}` deep link through the Windows URL handler;
errors surface through the canvas status message. Without Eagle source metadata
or the Eagle Links service, the button is omitted. Same-process click evidence is
in `docs/validation-ui/2026-10-26-eagle-open-item.md`.
