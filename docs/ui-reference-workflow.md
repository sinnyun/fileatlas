# 按参考图实现界面

本流程约束人和 AI 的界面改动，补充 AGENTS.md。目标是让实际窗口保留用户选用稿的
视觉结构与可操作状态；仅修改文字、颜色或少数边距不构成按图完成。

## 1. 确定本次使用的设计

先读开发基线与当前功能计划，在 [活动参考入口](reference-ui/README.md) 找到对应画面。
优先顺序为：用户本次明确指令/选用稿 → 该界面的活动参考及配套说明 → 已接受开发基线
及 v5 通用样式 → 历史源界面。`vendor/photag-source` 决定沿用的数据语义和已有行为，
不能用来推翻已选用的新布局。新概念图需先按 AGENTS.md 生成、打开并检查后再编码；
修正已选用稿与实现的偏差时，直接落实该稿，不能重新生成一张接近现状的图替换验收目标。

必须使用图像查看工具打开实际图片。只读提示词、Markdown 说明或代码均不足以了解画面。
遇到多状态拼图，应分别识别正常、录入、错误等状态，不能把各状态的内容同时堆到正常页。

## 2. 在编码前写出可检查的布局清单

将选用图旁的 `.md` 说明更新为本次实现清单，至少记录这些方面：

- 外框、导航、标题、正文、页脚的层级、相对比例、固定和滚动区域。
- 每一组内容的顺序，行/列对齐，控件相邻关系及占用宽度。例如命令/范围/按键/操作
  在同一横行，不能实现为“文本一行、按钮下一行”后仍声称保持了该布局。
- 字号层级、文字对比、内边距、行高、分区间距、分隔线和强调色。
- 常态、悬停、焦点、选中、录入、冲突、禁用、空数据、长文本和小窗口的表现。
- 图中文字中哪些是真实功能，哪些只是样例或图像瑕疵。所有控件绑定真实行为；
  示例标签和错误不能写死为默认页面数据。

“不按图片像素测量”只表示要适配 GPUI 布局、DPI、字体和窗口约束，不表示布局可随意改写。
不要逐像素复制图像噪点或生成错误；保留设计中可识别的信息层级、密度和操作关系。
若功能演进必须改变某项，写明具体差异、依据和影响，不能静默降低完成标准。

## 3. 实现与行为检查

2026-10-18 起，所有界面的配色、公共控件、字体与间距遵守
[工作台统一主题](ui-theme.md)。历史参考图继续决定业务布局和状态，但不再各自决定
一套 palette。先复用 UI Bridge `theme` / `components` / `panels`，并运行
`node scripts/check-ui-theme.cjs`，禁止为匹配单页历史截图重新引入独立主题。

复用现有 GPUI Kit、主题 token、通用浮窗及 Cordis 生命周期，避免重建整套设施。
渲染中的文字和数据来自真实服务，遵循 ReadModel 与 refresh contract。
设置更改仍走既有持久化入口；切换页面或关闭面板应清理录入态等临时状态。
大文件按页面/组件拆分。通过 fmt、locked 编译和项目治理守卫后，进行运行时核对。

## 4. 同进程 MCP 对照，修正后再验收

通过 `scripts/photag-mcp-debug.cjs` 启动 `photag-shell --mcp`，使用隔离的 dev-test profile。
实际点击可见控件进入状态，拍摄正常页、录入页、真实冲突/错误和小窗口，检查内容末尾。
状态 API 和断言用于证明行为；图片必须另外打开并与参考图逐项对照。
编译成功、截图文件存在、JSON 状态正确都不等于视觉通过。

在默认窗口先核对整体比例，再核对列、字号、留白与状态。检查截图来源是否为刚构建的 EXE、
同一 MCP 进程和本次运行，避免复用旧图。若默认图要求 F1–F9 全部可见，应优先修正默认
面板大小和内容密度；小窗口才使用滚动。不能以“可滚动”代替默认布局要求。
小窗口下不裁切关键操作，页脚保持可见；必要时有滚动退化并记录。

发现可见偏差后应修正并重新截图，不能一边承认偏差一边写“符合参考图”。若受外部条件
阻塞，列出准确阻塞和未验项目，保留“未验证/部分完成”，不改成“通过”。

## 5. 交付证据

在 `docs/validation-ui/<日期-功能>/` 保存可复现的 MCP 场景入口和简洁 Markdown 结论；
截图、完整 MCP 报告、日志、profile 与 fixture 放到 Git 忽略的
`.local/validation/artifacts/<日期-功能>/`、`.local/validation/profiles/<运行名>/`。
脚本可提交，运行产生的数据不能提交。Markdown 可以指向同路径的本地 artifact，
并需写明完整报告/截图的本机位置。默认使用 `scripts/photag-mcp-debug.cjs` 的
`.local/validation/profiles/`，不要将新产物写进 `docs/validation-ui/` 或 `target/`。
在 `docs/redesign-validation.md` 链接相应的人类可读 Markdown 结论。至少包含：

| 检查项 | 参考要求 | 实际表现 | 证据/剩余差异 |
|---|---|---|---|
| 外框与分区 | 写具体布局 | 通过或具体差异 | 图片与 viewport/DPI |
| 行列与字体 | 写对应控件关系 | 通过或具体差异 | 图片 |
| 状态与行为 | 写实际触发方式 | 通过/未验 | 场景、断言、状态图 |
| 小窗口与长内容 | 写可接受退化 | 通过/未验 | 缩窗/长文本截图 |

记录准确的构建和 MCP 命令、系统与 DPI、隔离 profile、哪些检查没有执行。
功能验证和视觉验收分别给结论；以后新截图推翻旧结论时，对旧记录明确追加更正。
