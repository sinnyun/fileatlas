The bounded in-memory buffer retains up to 10,000 records and resets at process restart. It captures application tracing/log events, structured operation spans, panics, explicit MCP actions and worker duration fields; native OS internals and process-abort crash dumps are not observable through this panel. Worker spans do not automatically propagate parent context across every thread boundary, and a cancelled span's elapsed time is not a business-success signal. RMCP transport DEBUG/TRACE payloads are suppressed to avoid recording the panel's own log-query response; MCP application actions and rejected requests are still recorded.

## Follow-up: selected inspector and render-triggered database reads

The first report showed repeated `database/with_reader` records because FileManager's virtual-list row processor called `FileManagerService::media_paths_by_ids` on every row redraw to build selected drag paths. A selected media record can leave the current 200-row loaded window after scrolling or multi-selection; the selection remains active, so the inspector and drag selection still need its metadata/path. The inspector also had a synchronous `media_by_id` fallback from render when that selected record was outside the loaded window.

Both read paths now run off the render path. On selection/window state, missing inspector media and tags are fetched once in a background task and cached; the inspector shows a loading state until the result arrives, then renders from the cache. Selected drag paths are assembled from loaded rows when possible, otherwise fetched once in the background and cached by selection IDs. A redraw no longer issues another database query. The selection remains valid across the window boundary and the right inspector continues showing the selected media.

Runtime regression: `node scripts/fileatlas-mcp-debug.cjs --exe target/debug/fileatlas-shell-inspector-async-debug.exe --profile target/mcp-inspector-async-final --plan target/inspector-async-live-plan.json --allow-mutations`. In one same-process MCP run, injected 1,000 isolated virtual rows, selected ID 1 while the FileManager loaded the first 200, and captured the live inspector. The right panel showed `virtual-000000.jpg` and its metadata while the visible grid showed `virtual-000999` onward. After selection settled, two `get_debug_info` reads 2.5 seconds apart both reported `latest_id=125` and `total=17`; there were six matching reader start/completion rows total from the one selection request, its MCP validation, and one drag-path resolution, with no additional records in the second read. Report, plan, and screenshot are archived beside this README.

Validation after the fix: locked tests for FileManager (19), i18n (4), and Debug (5) passed; the independent locked Shell binary build and selective rustfmt passed. Profile was isolated under target; no normal user data was changed.
